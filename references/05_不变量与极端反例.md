# 世界分析法阶段冻结05｜不变量与极端反例 v1.0

> **状态：阶段冻结**  
> **所属 Skill：** 世界分析法（world-analysis）  
> **作用：** 作为后续世界分析法 Skill 的正式设计事实源之一。

---

## 1. 定义

> **不变量与极端反例：识别候选模型在当前边界内必须持续保持的核心语义性质，映射其成立所依赖的关键前提、依赖与失效面，并针对这些位置主动构造有效反例尝试证伪；若发现击穿，则最小化反例以定位真正失效原因，从而判断模型是经受住攻击、边界过宽，还是存在结构缺陷。**

它回答两个核心问题：

```text
什么绝不能变？
什么最容易把当前结论击穿？
```

---

## 2. 适用场景

优先用于：

- 准备冻结核心理论；
- 生命周期、权限、可靠性、安全性规则；
- 声称“始终”“必须”“绝不”的结论；
- 已通过第一性约简和对抗性约简的模型；
- 怀疑理论只在正常路径成立时；
- 需要验证异常、恢复、并发、冲突、边界与未知结果时；
- 需要确认当前结论是稳定、边界过宽还是存在结构缺陷时。

通常不用于：

- 单纯事实查询；
- 尚未形成候选规则或模型的问题；
- 只需要比较两个竞争方案的问题；
- 只需要局部验证一次 Delete / Merge / Split 的问题。

---

## 3. 最小输入

```text
Analysis Target
要验证什么模型 / 规则？

Claim
当前核心结论是什么？

Scope
结论在哪些条件下声称成立？

Known Constraints
已经确认哪些外部硬约束？

Material Assumptions
当前结论依赖哪些关键前提？

Material Dependencies
当前结论依赖哪些关键外部或内部依赖？

Failure Meaning
什么情况算真正击穿当前模型？
```

其中 `Scope` 是必要输入。

原则：

> **超出原 Claim 适用边界的场景，不构成有效反例。**

---

## 4. 核心流程

不变量与极端反例正式冻结为：

```text
Extract Invariants
↓
Map Falsification Surfaces
↓
Attempt Falsification
↓
Minimize Counterexample
↓
Classify Result
```

---

## 5. Extract Invariants｜提取不变量

先识别：

> **在当前 Scope 和前提下，为了让模型自身语义保持正确，哪些性质必须持续成立？**

例如：

```text
Execution terminal
→ 不允许重新变成 running
```

这属于 Lifecycle Invariant。

又例如：

```text
只要 Durability Obligation 仍然存在
→ Physical Delete 不能自行解除该责任
```

这属于 Durability Invariant。

---

## 6. Invariant 与 Hard Constraint 的边界

两者不能混为一谈。

### Hard Constraint

来自问题或系统外部的约束、承诺或规则，例如：

- 用户明确要求；
- 业务规则；
- 法律限制；
- 权限边界；
- 产品承诺。

例如：

> 支付不能重复扣款。

### Invariant

是在既定前提和模型边界下，为维持模型自身语义一致性而必须持续成立的性质。

例如：

> 一个 terminal Execution 不重新打开。

关系：

```text
Hard Constraint
→ 可能推导出
Invariant
```

但：

```text
Hard Constraint
≠
Invariant
```

---

## 7. 与第一性事实的边界

第一性约简中的不可约语义用于：

> **构造模型。**

Invariant 用于：

> **验证模型建立后哪些性质必须始终保持。**

因此：

```text
Irreducible Semantic
→ 构模基础

Invariant
→ 模型稳定性要求
```

两者职责不同。

---

## 8. Map Falsification Surfaces｜映射证伪面

不要求枚举所有极端场景。

正式覆盖对象是：

```text
Material Assumptions
Material Dependencies
Core Invariants
```

针对每一类关键位置，寻找最可能让其失效的合法场景。

常见反例生成方向包括：

```text
Boundary
边界值 / 边界条件

Failure
组件或依赖失败

Conflict
多个规则或事实冲突

Concurrency
并发 / 重复 / 重试

Temporal
时间顺序变化 / 跨时间

Partial Success
部分成功

Unknown Outcome
结果未知

Authority Change
权限 / Owner 改变

Dependency Loss
依赖失效或暂时不可用
```

这些只是攻击方向，不是每次必须全部执行的固定清单。

---

## 9. Attempt Falsification｜主动尝试证伪

目标不是继续寻找支持案例。

而是：

> **主动构造一个仍处于原 Scope 内、原关键前提仍成立，但会导致当前 Claim 无法维持自身语义一致性的场景。**

例如：

```text
Claim：
所有 failed Execution 都可以直接 retry
```

有效攻击：

```text
外部支付已经成功
↓
本地未收到响应
↓
Runtime crash
↓
Outcome Unknown
```

如果当前模型无法表达或处理 `Outcome Unknown`，则说明原 Claim 被击穿。

---

## 10. 有效反例

一个反例至少满足：

```text
Within Scope
仍在原 Claim 适用边界内

Premises Hold
原关键前提没有被偷换

Real Semantic Conflict
确实造成模型语义冲突

Non-trivial
不是靠文字游戏或定义偷换制造
```

否则应判定为：

> **Scope Violation**

而不是模型失败。

---

## 11. Minimize Counterexample｜最小化反例

发现可击穿场景后，应去掉所有无关条件，直到只保留：

> **足以导致失败的最小条件集合。**

目的：

- 确认真正失效的前提；
- 避免复杂场景掩盖根因；
- 防止把无关因素误当成模型缺陷。

例如：

```text
支付成功
+
响应丢失
+
本地不知道结果
```

如果这已经足以击穿规则，就不需要继续加入更多异常条件。

原则：

> **反例越小，通常越有解释力。**

---

## 12. “极端”的正确含义

“极端反例”名称保留，但正式冻结：

> **极端不是反例有效性的必要条件。**

目标不是寻找最夸张的灾难场景，而是：

> **寻找最合法、最有杀伤力、最小的证伪条件。**

Boundary / Failure / Conflict 等只是帮助发现反例的方向。

---

## 13. Material Falsification Coverage

本方法不采用：

> “尽可能多测试场景”

作为覆盖标准。

也不要求 Agent 自行打风险分。

正式采用：

> **Material Falsification Coverage**

即：

> **针对当前 Claim 的每个关键前提、关键依赖和核心 Invariant，至少进行一次有针对性的有效证伪尝试。**

覆盖的是：

> **Failure Mechanism｜失效机制**

而不是：

> 场景数量。

---

## 14. Classify Result｜结果分类

正式允许四类 Verdict：

```text
Survives
Boundary Found
Model Defect
Insufficient Evidence
```

### 14.1 Survives

关键证伪面已经受到攻击，尚未发现有效击穿。

注意：

> **Survives 不等于证明理论永远正确。**

只表示：

> 当前高价值证伪尝试尚未推翻它。

---

### 14.2 Boundary Found

发现了合法反例，但真正说明的是：

> 原 Claim 的 Scope 写得过宽。

此时应：

```text
缩小 Scope
↓
重新表达 Claim
↓
再次验证
```

---

### 14.3 Model Defect

在原 Scope、关键前提和约束仍成立的情况下，出现真实语义冲突。

说明：

> 当前模型内部存在缺陷，需要修正。

---

### 14.4 Insufficient Evidence

无法确认某个关键反例的前提、依赖或结果是否真实成立。

此时不能制造结论。

应转入：

- 外部证据校核；
- 最小实证；
- 补充事实确认。

---

## 15. 与对抗性约简中的局部反例边界

两者职责不同：

```text
对抗性约简
Local Counterexample
→ 验证一次 Delete / Merge / Split 是否过度
```

```text
不变量与极端反例
→ 对整个 Claim / Model 做系统性证伪
```

因此：

> **局部反例是结构操作校验器；本方法验证的是整个理论或模型的稳定边界。**

---

## 16. 与双向钢人的边界

双向钢人：

```text
→ 比较两个最强竞争解释谁更站得住
```

不变量与极端反例：

```text
→ 主动尝试击穿一个已经形成的 Claim / Model
```

如果问题核心是：

> “A 还是 B？”

优先使用双向钢人。

如果问题核心是：

> “这个结论到底扛不扛得住？”

优先使用不变量与极端反例。

---

## 17. 停止条件

正式停止条件：

> **当前 Claim 的所有 Material Assumptions、Material Dependencies 和 Core Invariants 都已经受到至少一次针对性证伪尝试；新增案例只是在重复已有失效机制，不再暴露新的模型缺陷或适用边界。**

可简化为：

```text
关键前提 → 已攻击
关键依赖 → 已攻击
核心 Invariant → 已攻击
新增案例 → 无新 Failure Mechanism
↓
Stop
```

不要求穷尽所有可能场景。

---

## 18. 输出

默认输出保持简洁：

```text
【验证目标】

【Claim 与 Scope】

【核心 Invariants】
1.
2.
3.

【关键证伪面】
- Material Assumptions
- Material Dependencies
- Core Invariants

【最小有效反例】

【发现的边界 / 缺陷】

【修正后的 Claim / Model】

【Verdict】
Survives / Boundary Found / Model Defect / Insufficient Evidence
```

不默认输出完整推理流水账。

## 19. 硬约束

正式冻结：

1. **Invariant 是模型自身必须保持的语义性质，不等于外部 Hard Constraint。**
2. **第一性事实用于构模，Invariant 用于验证模型稳定性。**
3. **反例必须处于原 Claim 的 Scope 内。**
4. **反例必须保持原关键前提，不得通过偷换定义制造失败。**
5. **测试目标是尝试证伪，不是继续寻找支持案例。**
6. **覆盖的是关键失效机制，不是场景数量。**
7. **不得通过 Agent 自行打主观风险分决定覆盖充分性。**
8. **发现反例后应最小化，以定位真正失效原因。**
9. **极端不是目标，最小有效击穿才是目标。**
10. **Survives 不等于证明理论永久正确。**
11. **发现 Scope 过宽时应输出 Boundary Found，而不是直接判定 Model Defect。**
12. **证据不足时应输出 Insufficient Evidence。**
13. **本方法不能取代对抗性约简中的 Local Counterexample。**
14. **本方法不能取代双向钢人、外部证据校核或最小实证。**
15. **不得为了证明方法有效而强行制造反例。**

---

## 20. 典型误用

### 误用一：把外部要求当作 Invariant

错误：

> “用户要求数据保留 30 天”就是系统 Invariant。

正确：

> 这是 Hard Constraint / Commitment，它可能进一步推导出某些 Durability Invariant。

---

### 误用二：无限枚举异常场景

错误：

> 把所有能想到的 crash、timeout、network error 都跑一遍。

正确：

> 针对不同失效机制进行覆盖；重复机制不需要无限增加案例。

---

### 误用三：用 Scope 外场景推翻理论

错误：

> 一个只针对单机 Runtime 的 Claim，被多区域灾难场景“击穿”。

如果原 Scope 从未包含多区域场景，则属于：

> Scope Violation。

---

### 误用四：找到复杂反例后直接修改模型

正确做法：

```text
Counterexample
↓
Minimize
↓
定位真正失效条件
↓
判断 Boundary / Defect
```

---

### 误用五：把 Survives 当成证明

正确理解：

> 当前证伪尝试未推翻，不等于绝对真理。

---

## 21. 已验证场景

当前方法已通过以下不同类型理论验证：

### Terminal Execution 不重新打开

结果：

> `Survives`

Runtime Crash Recovery 需要继续原工作，但不要求复活原 Execution Attempt。

---

### Physical Delete ≠ Obligation End

结果：

> `Survives`

用户删除 Memory 的最小语义仍然是：

```text
Authorized Commitment Change
↓
Obligation End
↓
Physical Delete
```

而不是 Delete 自行定义 Obligation End。

---

### 所有长任务都应该支持 Resume

结果：

```text
原强 Claim
→ Model Defect / Boundary Found
```

最小反例：

> 长时间只读、完全可重放、无外部副作用且重跑成本可接受的任务。

验证：

> `Long ≠ Resumable`

---

### Durability Satisfaction 两种基本模式

候选：

```text
Directly Preserved
Reliably Reconstructed
```

通过外部保存、Replication、Backup、Reference、Snapshot + Replay、Re-acquisition、AI 重生成等不同机制攻击后：

> 未发现第三种不可归约 Satisfaction Pattern。

结果：

> `Survives`

---

## 22. 重新打开条件

只有出现以下情况才重新打开本阶段：

1. Material Assumptions / Dependencies / Invariants 三类证伪面无法覆盖重要模型问题；
2. Minimal Counterexample 在实际使用中无法稳定定位失效原因；
3. Verdict 四分类无法覆盖重要结果；
4. 方法频繁把 Scope Violation 误判为 Model Defect；
5. 方法频繁产生无限异常枚举；
6. 与对抗性约简的 Local Counterexample 边界无法维持；
7. 新实证显示该方法存在系统性漏检或伪反例问题。

---

## 23. 阶段冻结结论

不变量与极端反例正式冻结为：

```text
Extract Invariants
↓
Map Falsification Surfaces
↓
Attempt Falsification
↓
Minimize Counterexample
↓
Classify Result
```

合法结果：

```text
Survives
Boundary Found
Model Defect
Insufficient Evidence
```

核心判断：

> **不是寻找最夸张的极端场景，而是系统性攻击 Claim 的关键失效面，并寻找最小、合法、最有杀伤力的证伪条件。**

停止原则：

> **关键前提、关键依赖和核心 Invariant 都已受到针对性攻击，新增案例只重复已有 Failure Mechanism。**
